# Calibration Repeatability and Uncertainty Review

## Purpose

A single bench capture can produce a numerically good fit while still hiding run-to-run drift, setup mistakes, board mismatch, or weak reference instrumentation. ForgeSense therefore separates calibration capture from calibration review.

`tools/review_calibration.py` compares repeated `forgesense.calibration_proposal.v1` artifacts and decides whether the retained evidence is internally consistent enough for engineering review.

A passing result does not apply calibration and does not approve a safety-limit change. It only marks the evidence package as review-ready.

## Required evidence

The default review policy requires at least three independent bench runs produced from the same:

- FPGA board revision;
- ESP32-S3 board revision;
- sensor-board revision;
- repository commit;
- documented measurement method.

Each source proposal must retain its capture SHA-256 and must preserve the review-only authority flags generated by `tools/capture_calibration.py`.

The capture template also carries declared expanded reference uncertainty (`k=2`) for:

- current reference measurement in mA;
- temperature reference measurement in degrees C;
- accelerometer reference/orientation in mg.

These values must come from the actual instrument specification, calibration certificate, traceable reference method, or a documented conservative estimate. Do not copy the limits from the review policy into a capture and present them as measured uncertainty.

## Default review policy

The machine-readable starting policy is:

`hardware/calibration/calibration_review_policy_v1.json`

The policy currently requires three runs and checks:

- current gain spread across runs;
- current intercept spread;
- maximum current fit RMSE;
- temperature offset spread;
- maximum temperature residual RMSE;
- accelerometer bias spread for X/Y/Z;
- maximum within-run accelerometer standard deviation;
- maximum absolute accelerometer bias;
- declared reference uncertainty limits;
- identical board revisions;
- identical repository commit.

The numerical limits are conservative engineering starting points for repeatability screening. They are not certified metrology limits and must be revised only from retained evidence and documented engineering justification.

## Capture uncertainty

Add the following block to each physical capture using real values:

```json
"measurement_uncertainty": {
  "reference_current_ma_k2": 0.0,
  "reference_temperature_c_k2": 0.0,
  "reference_accelerometer_mg_k2": 0.0
}
```

The zero values above show the field shape only. Replace them with defensible expanded uncertainty values before physical review.

When uncertainty is declared, `tools/capture_calibration.py` validates that all three values exist and are finite and non-negative. The values are then copied into the proposal provenance.

## Accelerometer noise evidence

Calibration capture now records population standard deviation for each stationary axis in addition to mean bias:

```text
axis_stddev_mg.x
axis_stddev_mg.y
axis_stddev_mg.z
```

This provides a simple within-run stability check. It is not a substitute for vibration bandwidth, scale-factor, cross-axis, mounting, or frequency-response characterization.

## Generate repeated proposals

For each independent bench run:

```bash
python tools/capture_calibration.py evidence/cal-run-01.json --out build/cal-run-01-proposal.json
python tools/capture_calibration.py evidence/cal-run-02.json --out build/cal-run-02-proposal.json
python tools/capture_calibration.py evidence/cal-run-03.json --out build/cal-run-03-proposal.json
```

Do not edit generated proposal numbers by hand. Correct the source capture and regenerate instead.

## Run the review

```bash
python tools/review_calibration.py \
  build/cal-run-01-proposal.json \
  build/cal-run-02-proposal.json \
  build/cal-run-03-proposal.json \
  --policy hardware/calibration/calibration_review_policy_v1.json \
  --out build/calibration-review.json
```

The command exits successfully only when `review_ready` is true.

## Review output

The output schema is `forgesense.calibration_review.v1` and contains:

- source capture identifiers;
- canonical SHA-256 values for every source proposal;
- board and repository consistency checks;
- run count and minimum-run gate;
- current mean coefficient candidates and run-to-run spread;
- temperature mean offset candidate and spread;
- accelerometer mean bias candidates and spread;
- maximum within-run accelerometer standard deviation;
- declared reference uncertainty completeness and limit checks;
- conservative engineering uncertainty proxies;
- final `review_ready` state.

The mean coefficient values remain candidates. They are not automatically converted into firmware or FPGA constants.

## Engineering uncertainty proxy

The review utility reports a conservative `k=2` engineering uncertainty proxy by combining:

- maximum observed residual/noise term;
- declared reference expanded uncertainty converted to a standard term;
- half of the observed run-to-run span where the quantities share units.

The terms are combined by root-sum-square and expanded by a factor of two.

This is a screening metric for engineering review. It is not a complete GUM uncertainty budget, accredited calibration result, or certification claim. Additional contributors such as temperature coefficient, supply variation, ADC reference tolerance, shunt tolerance, amplifier gain/offset, mounting, bandwidth, and fixture effects must be evaluated before any production claim.

## Authority boundary

The review result always requires:

```text
reviewer_approval_required = true
source_control_change_required = true
automatic_runtime_application = false
may_relax_hard_safety_limits = false
```

A review-ready result therefore cannot update the ESP32-S3, rewrite FPGA constants, flash coefficients, alter analog trip thresholds, or relax deterministic hard limits.

If measured evidence justifies a calibration change, that change must be made explicitly in source-controlled configuration or RTL/firmware constants, followed by the normal verification suite and a separate engineering review. Protection limits require their own safety evidence and must not be inferred from a calibration fit.

## Verification

Run:

```bash
make calibration-check
```

This executes both single-run calibration tests and repeated-run review tests, then checks the source-level authority constraints.
